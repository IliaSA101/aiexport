# Выпуск версии

Чек-лист для каждой версии, которая уходит на GitHub. Проходить целиком, по порядку.
Выпуск идёт с Ubuntu: сборку, архивы и проверки артефактов делает `scripts/release.sh`.

## 1. Версия

Единственный источник — флаг сборки, файла-носителя нет. Его выставляет `scripts/release.sh`
из своего аргумента:

```
-ldflags "-X main.version=0.1.0"
```

Если флаг не передан, `main.buildVersion()` берёт версию из метаданных модуля (их пишет сам `go`), а при их отсутствии отдаёт `(dev)`. То есть рассинхрона между «версией в файле» и «версией в бинарнике» быть не может по построению.

Семвер: `0.X.0` — новая функциональность, `0.X.Y` — исправления. Версия видна по `aiexport --version` и пишется в лог при запуске.

Строку в «Что нового» (внизу) писать для человека, без технических слов.

## 2. Проверки — всё зелёное, ноль предупреждений

```bash
scripts/check.sh --race --vuln --cross
```

На Windows тот же набор: `scripts/check.ps1 -Race -Vuln -Cross`.

- `--race` требует gcc. `CGO_ENABLED=1` только на этот шаг.
- `--vuln` — `govulncheck`, нужен интернет за свежей базой уязвимостей.
- `--cross` — сборка под windows, linux и darwin с `CGO_ENABLED=0`. Если упала — в зависимости затащили cgo, и «один бинарник под все ОС» больше не выполняется.

QA по `docs/QA.md`: пункты, затронутые циклом; консоль браузера без ошибок и предупреждений. Если менялся формат профилей (с 0.2) — открыть файл профилей прошлой версии и убедиться, что он читается.

**Журнал развилок версии просматривает владелец** — `docs/specs/<версия>/decisions.md`
(для 0.1 — `docs/specs/decisions.md`). Развилки по ходу версии решались без него, рекомендуемым
вариантом с записью; здесь он подтверждает их или отмечает, что переделать в следующей версии.

## 3. Сборка и архивы

Перед запуском закоммитить всё, включая строку «Что нового» (внизу): иначе скрипт откажет
(«дерево не чистое»), а в бинарнике будет `vcs.modified=true` или чужая ревизия.

```bash
scripts/release.sh 0.1.0
```

Нужны (выпуск идёт с Linux): GNU tar, coreutils, `zip`, `git`. На Ubuntu `zip` ставится не
всегда: `sudo apt install zip`.

Скрипт отказывается работать без `LICENSE`, на грязном рабочем дереве, при неотслеживаемых
файлах в дереве и если вшиваемый файл не отслеживается git. Грязное дерево можно обойти
пробным прогоном `--dirty`: он пишет в `dist/ВЕРСИЯ-dirty/`, боевой выпуск — в `dist/ВЕРСИЯ/`.
При `--dirty` везде появляется суффикс `-dirty`: архивы `aiexport-ВЕРСИЯ-dirty-OS-ARCH.*`,
`--version` печатает `aiexport ВЕРСИЯ-dirty`. Новые неотслеживаемые (но не игнорируемые) файлы
при `--dirty` допускаются с предупреждением; игнорируемые, попадающие в сборку, — отказ.
Без `--dirty` любой неотслеживаемый файл — отказ.
Набор файлов появляется в каталоге целиком или не появляется вовсе. Скрипт собирает пять целей —
linux amd64/arm64, darwin amd64/arm64, windows amd64 — с
`CGO_ENABLED=0 -trimpath -ldflags "-s -w -X main.version=…"` и кладёт в `dist/ВЕРСИЯ/`:

- архивы `aiexport-ВЕРСИЯ-OS-ARCH.tar.gz` (для windows — `.zip`); внутри каталог
  `aiexport-ВЕРСИЯ-OS-ARCH/` с бинарником, `README.md`, `LICENSE` и `THIRD_PARTY_NOTICES.txt`;
- файл `SHA256SUMS`.

`-s -w` убирают таблицу символов и отладочную информацию — бинарник меньше, на поведение не влияет.

`-trimpath` обязателен, и не ради размера: без него в бинарник попадают полные пути машины
сборки — каталог проекта и имя пользователя. Бинарник выкладывается публично, то есть это утечка.

Сам скрипт проверяет собранное: `go version -m` (флаги сборки и `vcs.modified`), отсутствие
путей машины в бинарниках, `--version` (версия — только так, запуском на своей платформе:
с `-trimpath` Go не пишет `-ldflags` в бинарник, см. `docs/specs/decisions.md` §12)
и настоящую выгрузку подкомандой `export` на своей платформе.
Искать именно пути машины, а не имя владельца репозитория: оно входит в путь модуля
`github.com/IliaSA101/aiexport` и честно встречается в бинарнике сотни раз — проверка на него
даёт ложную тревогу (проверено 20.10.2026: 176 совпадений, все до одного — имя модуля).

Падение скрипта — стоп: причину чинить, а не править скрипт под результат.

## 4. Смоук собранного бинарника руками, ~3 минуты

Проверять именно собранный файл из архива, а не `go run`: отличия бывают ровно в том, что вшивается через `embed.FS`.

1. Распаковать архив своей платформы в пустой каталог: `tar -xzf dist/0.1.0/aiexport-0.1.0-linux-amd64.tar.gz -C <каталог>`.
2. `cd <каталог>/aiexport-0.1.0-linux-amd64`, затем `./aiexport --version` — версия та, что собирали.
3. `./aiexport`: поднялся сервер, открылся браузер, форма работает, консоль чистая.
4. Основной сценарий целиком: два разных корня с подписями → превью токенов → сборка → проверить, что в выгрузке есть манифест, нет `vendor`/`node_modules`, а отчёт о пропусках непустой и честный.
5. Второй запуск при уже поднятом первом: внятное сообщение, а не `bind: address already in use`.
6. Без браузера: файл на месте, UTF-8 без BOM, переводы строк LF.

   ```bash
   ./aiexport export --src "full|Мой модуль|/путь/к/проекту" \
                     --src "tree|Фронтенд|/путь/к/фронтенду" \
                     --out /путь/к/bundle.md
   ```

   Флаги: `--src` (режим|подпись|путь, повторяется), `--out` (обязательно), `--exclude`,
   `--no-gitignore`, `--max-size`, `--instructions`, `--force`.
7. Лог: строка «запуск, версия X», ошибок и предупреждений нет.

## 5. Windows

`.exe` проверяется на настоящей Windows: запуск двойным кликом, форма, одна выгрузка,
`aiexport.exe --version`. Эмуляция и Wine не заменяют: SmartScreen и пути с буквой диска
видны только там.

Неподписанный `.exe`: при первом запуске Windows SmartScreen предупредит — «Подробнее» → «Выполнить в любом случае». Упомянуть в Release notes.

## 6. Публикация

- Коммиты уходят в `main` обычной историей (не сжимаем: репозиторий публичный, история — часть проекта).
- `README.md` на GitHub — главная инструкция для читателя. Отдельного документа для пользователя нет: пользователь здесь технический.
- **Порядок в конце.** Сначала коммит всего, включая «Что нового», и только потом
  `scripts/release.sh` (см. шаг 3). Перед тегом сверить `vcs.revision` из `go version -m` бинарника своей платформы с
  `git rev-parse HEAD`; тег ставится на этот же коммит.
- **Тег и Release создаёт владелец, не агент.** Push и публикация — только после его явного «да»:

  ```bash
  git push origin main
  git tag v0.1.0
  git push origin v0.1.0
  gh release create v0.1.0 dist/0.1.0/* --verify-tag --notes-file <файл с текстом «Что нового»>
  ```

  В Release попадают архивы всех пяти целей и `SHA256SUMS`.
