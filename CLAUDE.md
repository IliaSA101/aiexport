# Проект: aiexport — упаковщик кода для ИИ

## Что это

Кроссплатформенный инструмент, собирающий исходники проекта в один файл для передачи языковой модели. Один статический бинарник на Go с вшитым веб-UI: запустил — открылась форма, выбрал пути, нажал кнопку, получил файл.

Заменяет самописный скрипт `/bitrix/admin/adeAIAnalytics.php`, который требовал развёрнутого Битрикс24 и вынуждал выгружать сторонние проекты через git на сервер с Битриксом.

**Ниша.** Для обычных однокорневых проектов эту задачу уже решает [repomix](https://github.com/yamadashy/repomix), и он используется. `aiexport` нужен там, где repomix объективно слаб:
1. мультикорневые бандлы — сборка из произвольных путей разных корней с человеческими подписями;
2. профили с историей в UI, без правки JSON;
3. пикер по файловой системе удалённого сервера;
4. ноль внешних зависимостей (repomix — это Node.js).

## Источники правды

- **`docs/ТЗ.md`** — требования, приоритеты, что сознательно не делаем. Основной документ.
- **`docs/ПЛАН_v1.md`** — структура пакетов, принятые решения с обоснованиями, зависимости, открытые развилки.
- **`docs/ROADMAP.md`** — что входит в какую версию, порядок этапов и критерии готовности.
- **`docs/specs/`** — спеки циклов и `decisions.md`: развилки с обоснованием выбора (вопрос, варианты, выбор, почему).
- **`docs/QA.md`** — сценарии проверки веб-интерфейса.
- **`.claude/LOCAL.md`** — пути и особенности конкретной машины: где Go и линтеры, зачем
  `GOTMPDIR`, где лежат внешние документы ниже. Вне этого репозитория, на каждой машине свой.
- **`.claude/PROCESS.md`** — как ведётся работа: агенты, хуки, страница хода, режим работы.
  Вне этого репозитория, в приватной оснастке; там же `OPS.md` про устройство репозиториев
  и рабочий список задач.

При противоречии между ТЗ и кодом — спросить, не решать самостоятельно.

## Команды

Основная оболочка — bash (Linux). Для Windows рядом лежит `check.ps1` с теми же шагами и порогами:
два скрипта держать одинаковыми, правка одного без другого — расхождение, которое заметят поздно.

```bash
# Все проверки. Без флагов — быстро; --race в конце цикла; --vuln и --cross перед релизом
scripts/check.sh [--race] [--vuln] [--cross]

go build -ldflags "-X main.version=0.1.0" -o bin/aiexport ./cmd/aiexport
```

```powershell
# Windows
powershell -ExecutionPolicy Bypass -File scripts/check.ps1 [-Race] [-Vuln] [-Cross]
go build -ldflags "-X main.version=0.1.0" -o bin/aiexport.exe ./cmd/aiexport
```

Скрипты ищут Go и линтеры сами (PATH, затем `GOPATH/bin`). Где они на текущей машине — в `.claude/LOCAL.md`.

**`GOTMPDIR` нужен только на Windows с антивирусом**: тот ложно ловит тестовые exe, которые `go` собирает во временном каталоге системы. `check.ps1` выставляет его сам на `.gotmp`; для команд агентов на такой машине — `.claude/settings.local.json` → `env`. В общий `settings.json` его не класть: путь одной ОС ломает любую команду `go` на другой. `check.sh` отказывается работать, если унаследованный `GOTMPDIR` указывает в несуществующий каталог.

**Прототипы, разовые сборки и тестовые деревья — в `.gotmp/`** (он в `.gitignore`): одно место на всех, его знают хуки и `docs/QA.md`, а на Windows scratchpad лежит внутри `%TEMP%`, где антивирус ловит собранное. Текстовые заметки в scratchpad держать можно.

Хук pre-commit подключается один раз: `git config core.hooksPath scripts/git-hooks`. На Linux ему нужен бит исполнения (`chmod +x scripts/git-hooks/pre-commit`), иначе git молча его пропускает.

## Качество

- **Ноль warnings и errors везде**: сборка, линтеры, тесты, консоль браузера, лог, предупреждения git. Найденное чинить сразу либо осознанно глушить в `.golangci.yml` или через `//nolint:правило // причина`. Молча игнорировать нельзя.
- **Файл ≤ 600 строк и ≤ 30 КБ.** Резать по смыслу, а не механически. Гейт стоит в `check.sh` / `check.ps1` и в хуке `.claude/hooks/file-size.js`.
- **Маленькая правка — маленький тест.** Полный прогон, QA, ревью и security — один раз в конце крупного цикла, их запускает оркестратор.
- `-race` требует cgo, то есть gcc. Это **не** нарушает правило «без cgo»: оно про релизный бинарник. Релизная и кросс-сборка идут с `CGO_ENABLED=0` явным флагом, чтобы случайно затащенная cgo-зависимость падала на сборке, а не обнаруживалась при кросс-компиляции.

## Стратегия тестов

- **Модульные** — правила ignore, глобы, определение бинарности, нарезка скелета, парсинг конфига.
- **Интеграционные** — обход и сборка на реальных временных деревьях (`t.TempDir()`).
- **`internal/testkit`** — генератор тестовых деревьев с ловушками: NUL-байт, UTF-16 с BOM, CRLF, файл сверх лимита, симлинк-цикл, `.gitignore` с отрицаниями и вложенностью. Бинарных фикстур в git не держим; то, что всё же лежит в `testdata/`, git не нормализует (`.gitattributes`).
- **Фаззинг** — на всё, что парсит внешние данные: `FuzzGitignoreParse`, `FuzzGlob`, `FuzzSkeleton`.
- **Golden** — рендер Markdown; сохранённый профиль прошлой версии должен открываться.
- **Оракул** — ignore-движок против `git check-ignore --verbose` на реальных деревьях: git здесь эталонная реализация.
- **`-race`** — в конце цикла. HTTP-сервер обслуживает каждый запрос в своей горутине, гонки реальны.

## Стек и конвенции

- **Go 1.26+.** Стандартный layout: `cmd/`, `internal/`, `pkg/`.
- `context.Context` первым параметром во всех функциях с I/O.
- Оборачивание ошибок через `fmt.Errorf("...: %w", err)`.
- Никаких глобальных переменных.
- Structured logging (`log/slog`), graceful shutdown.
- Веб-UI вшивается через `embed.FS` — без сборки фронтенда, без CDN.
- **Cgo в v1 не использовать** — он ломает кросс-компиляцию одной командой, а один статический бинарник здесь ключевое требование.

Зависимости: `bmatcuk/doublestar/v4` (глобы), `pkoukk/tiktoken-go` + `tiktoken-go-loader` (токены o200k_base офлайн; словарь вшивается и даёт +12 МБ к бинарнику). Планируются: правила `gitleaks` (секреты, этап 6), YAML-парсер (профили, этап 4). Каждую новую зависимость обосновывать и фиксировать версию.

**Инструмент не ходит в сеть.** Это не умолчание, а требование: один самодостаточный бинарник. Любой сетевой вызов — сначала развилка владельцу.

## Критичные требования (детали в `docs/ТЗ.md`)

- **`.gitignore` поддерживать с первого дня.** Без этого первый же локальный запуск бесполезен: в замерах реального проекта `vendor` + `node_modules` дали 12 117 файлов из 12 531 (96,7%).
- **Фильтрация — чёрный список + проверка на NUL-байт, а не whitelist расширений.** Whitelist в старом скрипте тихо терял содержимое файлов: они попадали в выгрузку одним именем, и модель считала, что содержимое ей показали.
- **AST-сжатие в v1 не делать.** Обоснование — в `00_КОНТЕКСТ.md`, раздел 3.
